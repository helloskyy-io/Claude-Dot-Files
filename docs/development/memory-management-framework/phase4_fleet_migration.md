## The scope ruling that re-cut this phase, and the blocker it dissolved

**RULED BY THE OPERATOR, 2026-08-10: the V1 bash fleet is not a migration target and never was.** In substance: *V1 things get left in place and eventually retired when no longer needed; when they stop being used they are deleted. Stop placing so much emphasis on converting them one-for-one — that works for some and fails miserably for others, because what we are doing is fundamentally different.*

This phase previously spanned two fleets. It now spans one, and three things follow.

**1 · Requirement 1's *"in either fleet"* is VOID.** It is restated against the V2 tree below. `build.sh:277` and `build-minor.sh:281` keep greping prose for as long as those scripts are used, and that is the ruling rather than a gap — [`exit-protocol.md` §7](../../standards/exit-protocol.md) already said *"no parent branches on prose is **false for the bash fleet on purpose**, and any conformance claim is scoped to the V2 tree."* The ruling makes the phase agree with the protocol instead of contradicting it.

With bash out of scope there is no bash half to be throwaway, and requirement 1 no longer makes a claim about it. **The question itself is now answered** — left in place, retired when no longer needed — and is recorded as such in [`temporal-integration.md`](../temporal-integration/temporal-integration.md) § Open questions. **Nothing gates this phase's scheduling.**

**Surface 1 — the shadow prose parse — STAYS, and this is the phase's one open requirement.**

*(The figures are [Phase 3 step 7b](phase3_typed_exit_record.md#step-7b--the-run-set-nine-live-dispatches-and-the-three-numbers-it-yields)'s and are pointed at rather than re-derived; a re-measurement should have one place to land.)*

**Both `channels_agree: false` rows are rule R1 firing — the parent applying a safety rule the model could not see — and on both, the child's typed `outcome` matched the prose shadow exactly.** So the two channels did not disagree about the review even once in the instrumented set.

**And that is still not enough to remove a protection. Four reasons, none of which a larger N from THIS phase fixes on its own:**

1. **The denominator is eight, over four PRs, three of them repeat passes on one PR.** The runs are not independent, and Phase 3 says so in its own words.
2. **The set spans a commit range, not a build** — `9fa69ff..41a0589` — and the child prompt changed between rows 2 and 3, on the row the set's most-cited finding rests on.
3. **C-45bhs5cm's blindness is structural.** `channels_agree` can only ever be written on runs where the incumbent prose channel already succeeded, so the agreement figure is conditioned on the very thing it measures. Widening the denominator does not remove it.
4. **The one channel failure in the set was on the prose side because THIS COMPONENT'S OWN CHANGE put it there** (Phase 3's Stage 6 ordering, fixed by `fb85c3e`). The nine dispatches therefore say nothing about how prose behaves when nothing upstream of it has changed — which is precisely the question a removal decision needs answered.

**AND RETENTION IS NOT FREE — the other side of the ledger, added by the refine pass because the draft priced only one.** The four reasons above are all costs of REMOVING. The cost of KEEPING, measured on the same run set: `review_pr_workflow` **raises** on disagreement; that raise fired on **2 of 8** instrumented runs; and on **both, the two channels agreed about the review** — they were rule R1 firing, the parent applying a safety rule the model could not see. So two instrumented runs were terminated after a completed ~40-minute review had already been posted and already routed, by a comparator that decides nothing, and **every firing to date was a false alarm with respect to the property it measures.** The durable evidence survives the raise (`append_parent_route` is written before it, deliberately), which is what makes the raise's cost separable from the shadow's value.

> **A criterion that prices one side can only ever resolve one way, so it is restated two-sided.** The shadow goes when the disagreement rate over a set of independent runs is low enough to trust the typed channel alone — **OR SOONER, if the comparator's own false-termination rate makes retention the more expensive error.** Today the second figure is 2/8 and the first is unmeasurable at N=8 for the reasons above. **Whether the RAISE should be demoted to a loud note plus the existing durable event — ahead of, and independently of, removing the shadow — WAS an OPERATOR RULING, and it was TAKEN on 2026-08-11 — narrowly, for benign divergence only. This clause is left as the record of what the ruling was made on.** The brief governing this phase states that a divergence must stay a loud failure rather than a silent preference, and a dispatch does not overrule that on its own reading of the same eight runs. It is written down so the choice is visible rather than defaulted into.

**So the shadow is retained — but it no longer RAISES on a benign divergence, and nothing about requirement 1's routing claim depends on removing it.** *(Updated 2026-08-11: the operator ruled the raise down to a loud note after it was measured destroying completed reviews at 2 firings in 8 runs, both `permission_denied`, both with the channels agreeing about the review. The demotion is NARROW — `permission_denied` and `denials_unreadable` print a banner and continue; `record_absent`, `record_stale`, `record_unparseable`, `envelope_unreadable` and `schema_version_unknown` still raise, because those mean the typed channel produced no opinion at all and there is nothing to diverge from. The two-sided ledger above is what the ruling was made on and stays as the record of it.)* — a non-routing comparator is not a parent branching on prose. **What this phase contributes toward the removal is the denominator itself:** every `review-pr` dispatch writes a `parent_route` event carrying `channels_agree`, `shadow_verdict` and `shadow_parseable`, and [Phase 6](phase6_read_what_it_writes.md) owns the reader that turns those into a rate. **Removing the shadow on the strength of the design rather than the data is the failure this phase is structured to avoid, and eight runs is the data.**

> **The alternative was available and is rejected explicitly rather than left unmentioned:** this pass could have removed the shadow and reported requirement 1 fully met. It would have been the more flattering read of the same evidence, and it is the one a summary would copy — the same shape Phase 3's step 7b had to withdraw.

## Notes and gotchas

- **The phase got smaller and the enumeration did not get easier.** Dropping V1 removes roughly half the declared surface, but what would break this phase was never breadth — it is a call site nobody enumerated, or a grep whose pattern only matches one shape. A V2-only sweep written with the bash spelling (`COMPLETION_PATTERN=`) returns **zero hits**, which reads as "nothing to do" rather than as a broken pattern. Every enumeration in this doc carries the command that produces it for that reason.
- **Do not re-derive a count from a previous count.** Three times in two days a figure in this repo was right with a wrong derivation, or computed from an earlier copy of itself. Where this plan states a number, run the command beside it.
- **The two-declaration failure is the one this repo has already had**, and it is still live in this phase's surface: `extract_pr_url` exists twice. The cross-language version of the problem is closed by the scope ruling; the intra-tree version is not.
- **Do not let a refactor move aggregation into the parent.** The child derives its verdict from its own findings and states it; a parent re-deriving one is a caller with no stake making a judgement about the child's judgement. This is correct in the shipped code today and the migration must keep it correct.
- **Splitting this phase by consumer is RULED, not left open** — see the note under requirement 1. The other nine V2 `COMPLETION_PATTERN` children are deferred with a named trigger, because migrating them adds a producer with no consumer. *This note previously left the choice open with "both are defensible", which is how a phase acquires two completion bars.*
- **This phase writes a `parent_route` event on every routed run and reads none of them.** So does [Phase 5](phase5_convergence_stopping.md) with `convergence`, and so does the resource telemetry with `run_resources`. [Phase 6](phase6_read_what_it_writes.md) owns that. **The ordering is PER READER, not per phase, and [Phase 6 § Dependencies](phase6_read_what_it_writes.md) is authoritative for it** — *only the `parent_route` reader should follow this phase.* `run_resources` is already fleet-wide (`append_run_resources` is called from `run_claude`, which every V2 child passes through), and `convergence` will never widen (findings come from one child), so both of their readers may start immediately. *This bullet previously sequenced all of Phase 6 behind this one on the "a reader built before the fleet-wide denominator exists measures one parent" argument; that argument holds for one of the three members, and applying it to all three defers the two numbers the 2026-08-10 livelock left nobody able to establish.*
