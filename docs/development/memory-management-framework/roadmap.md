## What this component is

Two kinds of memory exist because a context window ends and the work does not. They differ in **who reads them**.

- **Kind 1 — the durable record, read by humans and AI.** Built, in use, and **documented as a framework by [Phase 2](phase2_kind1_framework.md)**: [`memory-model.md`](../../guide/memory-model.md) states it as five substrate-free properties, of which this fleet ships **two bindings across five surfaces** — three GitHub surfaces whose to-do bit is `open` (PR threads for change-outcomes, Issues for no-change outcomes, the standup tracker for continuity), and two committed markdown tables whose to-do bit is a `status:` column (`direction.md` for operator rulings, `candidates.md` for research candidates and their dispositions).
- **Kind 2 — a typed record the child writes at exit, on a channel the parent owns, read by CODE.** Not built. A parent must decide *in code, with no model in the loop*, which child to invoke next.

This component owns: the typed record and its schema; what a parent may route on without a model in the loop; how that relates to the durable human-readable record already in git; and the fail-safe contract when the record is absent or malformed.

**It does not own:** whether to build this (settled — [`sprint.md`](../sprint.md)); the product-level thesis about code-routed control flow (settled — `docs/standards/architecture/research/raw/code_routed_control_flow.md` §6.6, "ordinary as stated"); or the Temporal port ([`temporal-integration/`](../temporal-integration/temporal-integration.md)). Citing those is correct; re-opening them is not.

## Why six phases, and why the splits fall where they do

The test this plan applies: **a phase ends where something works end-to-end, and a phase that grows past one verifiable outcome gets split.** Applying it to this component's evidence produced five, not the four milestones the sprint entry lists and not one. **A sixth was added on 2026-08-10 by applying the same test to what the first five had shipped** — see item 5 — rather than by growing the scope of any of them:

1. **Measurement is its own phase because its readout can cancel work in the phases after it.** The research is explicit that two of the experiments are cheap and *either can move the design* — if `is_error` never disagrees with the shell's propagated exit status, the "read the rest of the envelope" milestone is a no-op and must say so; if the prose grep has never missed across the archived logs, the transport upgrade buys nothing measurable at this scale and the justification order changes. A measurement folded in as the first checklist item of a design phase is a gate the same run walks straight past on its way to the design it already intended to write. As a phase boundary it is a ruling with a human in between. It is also *prove-by-hand-before-automating* applied literally.
2. **Documenting Kind 1 is separable from building Kind 2, and it is a precondition for it.** Kind 1 is built and in use; writing it down is an authoring task with its own done-state. [Phase 3](phase3_typed_exit_record.md) cannot specify a schema without knowing what the human record carries as prose — anything the schema does not model, the render loses — so this lands before it. It depends on nothing in [Phase 1](phase1_measure_the_channel.md).
3. **Design-and-prove-one-pair is depth; migrating the fleet is breadth.** They have different verification: Phase 3 is done when one parent routes on one child's typed record end-to-end with the prose channel still in place; ~~[Phase 4](phase4_fleet_migration.md) is done when every child emits one and no call site parses prose.~~ **RE-CUT 2026-08-10 — Phase 4 is done when no parent in the V2 tree parses prose, which is TWO surfaces; child emission is `review-pr` only and the other nine are deferred on a named trigger. See [its requirement 1](phase4_fleet_migration.md#requirements-for-completion), which is authoritative.** *(Struck rather than rewritten: this sentence is the phase-count rationale, read before anyone reaches requirement 1, and it carried the pre-ruling bar — the same 10× sizing ambiguity the re-cut fixed one section over.)* The depth/breadth split the item is making survives the re-cut unchanged. Bundled, the design's proof would be indistinguishable from the migration's completeness, and the phase would become a project.
4. **Convergence stopping is a separate capability with a separate failure mode** — a stopping rule that fires early ends productive work silently, with no failing test. It needs typed comparable records from the one child that emits findings, which [Phase 3](phase3_typed_exit_record.md) delivers; it does **not** need the fleet-wide rollout, so it can run alongside [Phase 4](phase4_fleet_migration.md) rather than behind it.
5. **Reading what the component writes is a phase because emitting and consuming are different verifiable outcomes, and the fleet has now shipped three of the first and none of the second.** [Phase 3](phase3_typed_exit_record.md) added `parent_route`, [Phase 5](phase5_convergence_stopping.md) added `convergence`, and the resource telemetry (`0feacc3`) added `run_resources` — all to the same per-run JSONL log, each by a different phase, and `grep -rln "parent_route\|run_resources\|\"convergence\"" scripts/helpers/measure/` returns nothing. Folded into any of those phases, the reader would have been the last checklist item of a phase whose headline was already met, and the pattern says what happens then: **two of the three shipped without a reader, and only one of those two placed a candidate for it.** As its own phase it also carries the thing nobody else claimed — [Phase 5](phase5_convergence_stopping.md)'s requirement 5 says the rule is validated *"before it gates anything live"* and **no phase owned ever gating it live**, so the component could complete with a predicate nobody enabled. [Phase 6](phase6_read_what_it_writes.md) owns the instrument; the ruling stays the operator's.

### [Phase 5 — Convergence-based stopping](phase5_convergence_stopping.md)

Replaces a model-asserted convergence flag with a computed one. `review-pr` already emits `converged: true|false` — a single-pass severity heuristic the model decides and **nothing routes on** — and already mandates stable finding ids reused verbatim across passes. This phase turns convergence into a class-(ii) computed signal over those ids. **Amended by [Phase 1](phase1_measure_the_channel.md) E7 (2026-08-08), and the amendment is load-bearing:** the predicate reads the **OPEN subset** — findings whose `disposition` is not one of `fixed`/`deferred`/`rejected`/`noted`/`escalated` (E7 left `escalated` open and handed the ruling to Phase 5, which ruled it **CLOSED**) — and its stopping condition is **the open set being EMPTY, not merely unchanged.** Measured over the whole archive: the delta over *all* ids has always been empty **0 times**, because the `pr_review:` block restates every prior id and the set therefore cannot shrink; over the open subset the set has reached zero on **two** PRs. *(Counts with their date and denominator live in [Phase 5 § Measurement](phase5_convergence_stopping.md) and are deliberately not restated here — E7's figures were superseded within a day of being written, and a summary line is a copy that drifts.)* *"Unchanged"* is the wrong condition and was measured wrong: at #58 pass 2→3 the open set held at 2 with nothing added and nothing closed, where a delta-based rule would have stopped and been **incorrect**. **`disposition` is the input, and Phase 5 must NOT build on a `severity` field** — `severity` appears on **none** of the archived findings, while `disposition` appears on all of them. Ships with the documented guards against a naive "nothing new" rule — an oscillating finding set, an adaptively biased reviewer, and a degraded pass that emits nothing are all indistinguishable from convergence unless the rule is written to tell them apart.

## Key Decisions

Decisions scoped to this component's design are recorded here rather than as separate numbered artifacts, per this repo's no-ADRs convention. Each rests on verified evidence and names it, and each names what it costs.

**Adopt arrangement A — one author, two copies, two lifetimes.** The child writes the typed record once at exit to a channel the parent owns; the human record is rendered from it; the durable copy on the PR is a by-product of that rendering rather than a second authoring act. *Why:* the hardest-looking constraint — durable human record, machine value needed seconds after exit — is a **storage** mismatch, not a content mismatch, and dissolves under A. *Rests on:* `dual_channel_outcome_records.md` §5, R1, R5 — derived, with its falsifiers in that paper's test plan. *Alternative rejected:* the current arrangement B (parse a typed value out of a human-authored artifact) is, across 26 sources, never shipped without a write-time gate, and is never used to route a *process outcome* — where an outcome routes a subsequent process, the arrangement is A or D, every time. **Costs:** everything the human reads must be expressible in the typed record, or the render loses it. GitHub's SARIF consumer implementing a documented subset and ignoring the rest is the general shape of that loss. [Phase 2](phase2_kind1_framework.md) enumerates the prose at risk so the cost is paid deliberately rather than discovered by an operator noticing something missing.

**Two viable transports, and the ruling criteria are isolation and replay cost, not just availability.** Either a JSON file at a caller-declared path, or `--output-format json --json-schema` with the parent reading `structured_output`. *Why the criteria matter:* `structured_output` keeps the handoff inside the CLI's own result envelope — runtime-written, schema-validated, no new filesystem write channel, no staleness class and no partial-record class at all — and it keeps the whole handoff inside one Temporal activity result, which matters because Temporal Integration is the thing this component unblocks. The file variant asks a child running under `--dangerously-skip-permissions` to write outside its worktree, which is the isolation boundary the fleet's safety argument rests on, and it introduces a second I/O boundary that must become its own activity. *Against that:* the file variant carries the same routing properties with no dependency on a high-volatility CLI feature. **[Phase 1](phase1_measure_the_channel.md) rules on both axes, not one** — and if the file variant wins, it arrives with the compensating requirements attached (fresh path per invocation, run identity, anchored outside the worktree, consumer-side completeness check). *Rests on:* `claude_code_integration_surface.md` §1; verified present in `--help` on CLI 2.1.224.

**Split the abstention member in two.** A computed *could-not-check* arm and an asserted *needs-a-ruling* arm. *Why:* every mature observable vocabulary surveyed has an abstention member — Kubernetes probes' `Unknown`, Argo's `Error` distinct from `Failed`, Monitoring Plugins' `Unknown`=3, pytest's exit 5 — and **all of them mean "the checker could not evaluate," never "the work is ambiguous."** `HOLD - needs-assistance` means the second. They have different reliability and different remedies, so one member doing both jobs is one member measuring nothing. *Rests on:* `non_model_observables.md` §5.5, §0 finding 3, P5. **Costs:** one more vocabulary member for every consumer to handle, and a migration for the existing single member. **This is the concrete change the sprint item does not contain.**

**Borrow the fail-safe contract; do not design one.** Kubernetes `podFailurePolicy` — ordered rules, first match wins, documented default — is the evaluation semantics; the residual arm is a **named state that gets recorded**, not a silent default. *Why:* routing on values the model did not author is mature and boring outside the agent corpus, and three first-party vocabularies converge on the same two members (GitLab `on_success`/`on_failure`, Airflow `all_success`/`one_failed`, GitHub Actions `success()`/`failure()`). Treating this as a design novelty is the error. *Rests on:* `non_model_observables.md` §2.1–2.2, §3.2, synthesis §5. **Costs:** nothing this component would otherwise spend; the shape is free and the alternative is inventing one.

**When an asserted verdict and a computed observable disagree, record both under distinct names.** GitHub Actions' `outcome`/`conclusion` split is the shape — the raw observation is never overwritten, the policy-adjusted value is what routing sees by default. *Why:* no surveyed system documents precedence between an asserted and a computed result, because none has an asserting producer. There is no prior art to borrow, so the fleet picks, and picking "keep both" costs one extra field and preserves the ability to change the ruling later. *Rests on:* `non_model_observables.md` §3.3, N1. **Constrained by Phase 1:** if the off-diagonal cells never occur, adopt the two-name shape and build no composition machinery.

**`permission_denials[]` is safety observability, not a routing option.** It is recorded and surfaced on every run regardless of any routing ruling, and a non-empty denial list routes to the human arm and **never** to automatic redispatch. *Why:* under `--dangerously-skip-permissions` the safety hook is the only control operating inside a headless run, and a denial does not fail the run — the array is the only trace it left. `grep -rn "permission_denial" scripts/` returns nothing today, so this component is the fleet's only scheduled opportunity to observe that control firing. Auto-redispatching a child that just tripped the safety floor is an unbounded retry loop against the one control there is. **Costs:** the observable cannot be closed as a no-op even if it never changes a route — that is the point.

**Justify the design by the stationary error rate, not by producer exceptionalism.** *Why:* CI has the well-formed-plausible-wrong-result problem too, and it is measured — 170 reruns for 95% confidence a pass is not flaky; 31.08% of SWE-Bench+'s *passed* patches suspicious on manual screening; `continue-on-error` shipped as a keyword that makes a green build over a failed step deliberate. What genuinely differs is that a CI step's malformedness is **a defect with a fix** whereas an LLM's is **a stationary rate with a distribution** — which changes the *fail-safe contract* (it must be total and must assume the bad case recurs), not the taxonomy. *Rests on:* `non_model_observables.md` §0 finding 2, P13. *Consequence:* "our producer is special" is a claim a CI-literate reviewer will break, and it appears in a standard today — see Standards-amendment candidates.

**Lead with the measurement argument, not the routing argument.** Convergence detection *requires* typed comparable finding records. The routing argument has a working incumbent: `build.sh`'s prose grep is fail-closed, its vocabulary is three closed tokens, `review-pr` fails loud on absence, and **no evidence in the pool shows that arrangement producing a wrong route.** *Why:* a doc claiming the current arrangement is broken is overclaiming, and Phase 1 exists to find out whether it can be claimed at all. **Note the incumbent on the measurement side too:** `review-pr` already emits a `converged` flag, so Phase 5 is a class-(iii)-to-class-(ii) replacement rather than greenfield — a narrower and more defensible claim than "nothing detects convergence." *Rests on:* `convergence_stopping.md` P11; `dual_channel_outcome_records.md` §7.0.1–7.0.2; `scripts/workflows/children/review-pr.sh:323,355`.

**Do not put the machine channel in git notes or commit trailers.** That family is arrangement-B metadata *about* a durable artifact and is never used to route a process outcome; notes additionally carry an unresolved transfer-semantics question. *Rests on:* `dual_channel_outcome_records.md` R7, N4. **The negative is the finding** — recorded so it is not re-proposed.

**Do not cite SARIF or Conventional Commits as precedent for arrangement A.** SARIF's `level` and `message` are sibling fields on one `result` object — arrangement C, not A; what looks like A is GitHub's *consumer* side, and the transferable lesson is the subset contract and the 10 MB cap. Conventional Commits presupposes a mutable pre-merge artifact (its documented remedy for a wrong value is an interactive rebase); a posted PR comment is not rebaseable. *Rests on:* `dual_channel_outcome_records.md` §7.0.6–7.0.7.

**Do not cite the GitHub Actions 1 MB / 50 MB output caps anywhere in this component.** They were not found in the fetched primary and are unverified wherever they are met. The one corroborated cap figure in this evidence base is Tekton's 4096 bytes. *Rests on:* `code_routed_control_flow.md` N4.

**The stall/liveness axis belongs to Fleet Reliability, not here.** "Did it stall?" is answerable in principle from runtime observables, but [`sprint.md`](../sprint.md) already places *the three-legged liveness predicate* in Fleet Reliability, and that component's pool has already measured the `stream-json` progress signals. *Why here at all:* the research surfaced it as an open scope call naming this component as a possible destination, and leaving a raised scope question unruled is how it gets built twice. **What this component owes it:** nothing but a check that nothing Phase 1 measures contradicts that paper's findings. *Rests on:* `non_model_observables.md` P8, P9, §5.1; `fleet-reliability/research/raw/liveness_signal_measurement.md`; sprint scope. **This ruling has a sprint implication and is surfaced for the operator, not written into the sprint file.**

A typed record carrying a `verdict` is a second state machine over the same work, and the corpus's only answer (Kubernetes: a condition is current state, an Event is history) is *neither closes the loop*. Nothing upstream decides this. Phase 1 counts the actual disagreements between `pr_review:` verdicts and their PRs' open/closed state; Phase 3 rules with that number in hand. *Rests on:* `dual_channel_outcome_records.md` §5 sub-problem 3, T3 — flagged in the synthesis as a **decision with no owner**, which this line gives one.
