**The consequence, and it is why this is a finding rather than a note about unfinished work: `plan-feature` ships today with NO sizing anywhere in the pipeline and NO fresh reader of its decomposition.** The other two families each have their judge and both state the same reason in their own docstrings — research is `research-write` -> `research-verify` because *"a separate fresh-context run verifies it... the run that wrote an artifact defends it"*, and build is `build-draft` -> `build-refine` because *"the fresh context is the point, not an implementation detail"*. Planning now has a producer with neither. **Two things are load-bearing rather than cosmetic.** (1) **Hours have no owner at all.** `plan-feature` deliberately estimates none — an author sizing their own decomposition is defending it — and its runner FAILS THE RUN on an hour figure, so the number does not exist anywhere until this lands. `plan-sprint` totals hours it is handed and derives none. (2) **`review-pr --type planning` is a PR reviewer, not a plan reviewer**: it judges the diff and the criteria in `criteria_planning.md`, and nothing in it reads a roadmap cold and asks whether the phase boundaries are the right ones. **What it would cover:** sizing per phase; whether each phase ends at one verifiable outcome; whether a producer shipped without its consumer; whether the evidence cited actually supports the phase; and the question `plan-feature`'s own report is required to ask and cannot answer about itself — *where is this plan weakest*. **Sized as its own workflow, not a stage**, on the same argument that made `triage-candidates` a separate run: a judge inside the producing dispatch shares the producer's context, which is the one property it exists not to have. **→ DELIVERED 2026-08-15** — `plan-verify` exists as a workflow, an entry script and a runner, is wired into `plan_project` between `plan-feature` and `plan-sprint`, and declares its own `MAY_NOT_OBSERVERS` / `DISAPPEARANCE_OBSERVERS` tables. `status` moves to `closed` because this row's work is BUILT; `decision` stays blank because it is `triage-candidates`' alone and nothing has ruled on it. **That justification originally cited "§ Where things stand already records six rows delivered before anyone got round to ruling them", and THAT CITATION WAS FALSE — corrected 2026-08-16 by this PR's refine pass.** § Where things stand records no such thing; the rows a reader would reach for as precedent (C-bn4r7lha, C-bj31mvd2–C-f5olzmns) all carry `decision: ship` with `status: open`, which is the OPPOSITE combination; and `grep` over the table returns **this row as the only one in the file with `decision` blank and `status: closed`**. So this is the first instance, not an established pattern, and it is stated as such: the two flags are orthogonal by this file's own § Two flags model, so the state is defensible, but nothing here had done it before and a reader should not be told otherwise. Whether "built ahead of triage" should close a row at all is a ruling for `triage-candidates`, and this row does not pre-empt it. **One thing it does NOT deliver, stated here so the next reader does not assume it:** the estimates land in `<component>/roadmap.md`, and `plan-sprint` cannot see them — its prompt states it never opens a phase doc, the block it is handed lists no roadmap, and it contains no reader for an hour figure, so it still sizes against its 160-hour calibration. That is a change to `plan-sprint` and is filed separately.
