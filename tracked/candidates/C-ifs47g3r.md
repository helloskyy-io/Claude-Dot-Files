**The consequence, and it is already happening rather than predicted: the four copies have DIVERGED.** `research_write/prompts/write.md`, `research_verify/prompts/verify.md`, `research_refresh/prompts/refresh.md` and the new `research_write_minor/prompts/write_minor.md` each end in a near-identical RULES block — Bash-CWD, Re-Read-before-Edit, large-file reading, parallel gather, the git-status check. They are not identical: `verify.md`'s relative-paths bullet is one line where `write.md`'s is a paragraph, and `refresh.md` carries an abbreviated set. **So the four workflows are being given materially different operating rules for the same hazards, and nothing anywhere records that this was a decision.** **The rule is already binding and already crossed:** [`temporal_standard.md` §10.1 rule 3](../../temporal/temporal_standard.md) — *"promoted OUT of a workflow's folder to the parent level if and only if MORE THAN ONE workflow uses it — consumer count decides, never taste"* — echoed for `.md` fragments specifically in [`claude-dot-files-addendum.md` §A4](../../temporal/claude-dot-files-addendum.md). The threshold was crossed at three copies, before PR #83 existed; that PR added the fourth. **The mechanism and the precedent both already exist:** `act.shared_prompt()` loads module-level fragments, and the build family already made exactly this migration — `build_draft`, `build_draft_minor`, `build_refine` and `build_refine_minor` all inject `${RULES}` from one `modules/assistant/prompts/rules.md`. **Why it was not simply done in PR #83, stated so the deferral can be judged rather than taken on trust:** the remedy is not an edit to the file that PR authored. Unifying four drifted copies means choosing which wording wins and then rewriting three prompts belonging to workflows that PR does not own — a change to what three live, verified workflows receive at dispatch, made incidentally inside a PR whose stated design principle is that the full research cycle stays byte-unaffected. **Done-state today: yes.** A `research`-purpose-level fragment plus the plumbing to load one (`shared_prompt()` currently resolves only against `modules/assistant/prompts/`, so a purpose-level fragment needs either a second loader or promotion all the way to module level — that choice is part of the work, not a blocker on it). **PROPOSAL, not a defect:** nothing behaves wrongly today, and each prompt is individually coherent. **Not an expansion of C-523klr8n or C-zwzepum0:** both concern a claim that is FALSE — a restated figure and a cross-file assertion.
