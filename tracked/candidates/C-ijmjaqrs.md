**`mutate.sh` classifies pytest's exit codes, and a target repo's own configuration can change which code pytest returns for the same event.** The table's load-bearing premise is *"pytest interrupts to 2 on a collection error unless `--continue-on-collection-errors`"*; with that flag in force a collection error returns **1**, which the harness reads as RED without ever consulting the exit-2 discriminator — issue #72's false certification, reached through configuration rather than through code. **Measured on this PR, not reasoned:** with `PYTEST_ADDOPTS=--continue-on-collection-errors` set, mutating the module under test into a `SyntaxError` printed `✓ MUTATION DEMONSTRATED` and exited 0 over a test that never ran. **The DEFECT half was fixed in PR #74 and is not this row**: `run_leg` now clears `PYTEST_ADDOPTS`, the false *"which this harness never passes"* justification is corrected, and `test_an_inherited_PYTEST_ADDOPTS_cannot_reopen_issue_72` pins it. **What remains is capability that does not exist:** `addopts` in the target's `pytest.ini` / `pyproject.toml` / `tox.ini` supplies the same flag and **cannot be cleared by an environment variable** — closing it means resolving the effective configuration before leg 1 (`--override-ini`, or parsing what `pytest --help`/`--co -q` reports) and refusing or adjusting when it conflicts. Nothing like that exists, and there is **no reproduction of the ini channel today** — this repo's own config sets no `addopts`, which is what keeps this a proposal rather than a second defect. That reproduction test is the discriminator used to split the two halves. **Not an expansion of C-45bhs5cm:** that row is about a leg that RAN but executed nothing, read out of a channel pytest does not expose; this is about the exit code itself meaning something different than the table assumes. Different mechanism, different remedy — but if either is ruled `ship` the other should be read alongside it, because both end at *the exit-code channel is too narrow to carry what this harness needs* and a `--junitxml` structured channel would answer both at once. **No done-state today and no phase owns it.** `mutate.sh` is repo tooling, not phase work; the harness's header markets it as portable (*"four independent runs on a sibling repo each hand-rolled this identical loop"*), so the ini channel becomes reachable the moment it is used outside this repo — which is the trigger, and it has not fired. **Cost of leaving it:** the one tool that decides whether every other guard is trustworthy can be silently mis-calibrated by a config file it does not read, and the failure is a false certification rather than an error.  *(Renumbered from C-73bf2gvm on 2026-08-11 — that ID was taken by an unrelated proposal on `main` while this branch was open.)*
