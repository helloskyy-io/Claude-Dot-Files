**Measured on this branch, and on the previous run's commit, so it is not an artifact of this pass.** `test_a_directory_the_map_ENUMERATES_is_enumerated_COMPLETELY` fails as soon as a phase doc is added to a directory the map enumerates file-by-file: `docs/file_structure.txt:155-158` lists `workflow-decomposition/` as `roadmap.md` + `research/`, so the four phase docs planned into it are holes. Reproduced at `6d71c75` (four docs) and at `a8846fb`, the previous run's tip (also four) — **that run's PR body asserted the opposite**, *"the map's coverage test passes (it checks the directory, not the phase list)"*, which is why this row states the command rather than the conclusion: `python3 -m pytest testing/scripts/tests/unit/test_file_structure_map_covers_the_tree.py`. **Why it is structural rather than one stale map.** `plan-feature`'s grant is markdown files sitting directly in the component directory, and the map is not one; its dispatch prompt names `docs/file_structure.txt` as out of scope explicitly. Writing a phase doc is the workflow's ENTIRE JOB, and the map enumerates at least two planning directories that way (`persistent-memory-protocol/` is the other, at `:108-113`). **So the next component `plan-feature` plans lands red for the same reason, and the run after that, until one of the two sides moves** — the failure is produced by the boundary, not by any run's carelessness, which is exactly the shape a single run cannot fix from inside. **Two remedies, and they are genuinely different rulings rather than one idea phrased twice.** (a) **Widen the boundary by one line** — permit the workflow to edit only its own component's block in the map, checked the way the phase-doc filename check already is. Keeps the map's per-file annotations, which are load-bearing prose a reader uses; costs a carve-out in a boundary whose value is that it is narrow, and hands an LLM producer a file every other component also lives in. (b) **Let the map roll planning directories up** — a `roadmap + N phase docs` summary line instead of per-file entries, which the test already supports (it only enforces completeness on directories the map chooses to enumerate). Cheaper and keeps the boundary intact; costs the per-phase annotations for those directories. **Not an expansion of C-npx1uwgj**, which is about a duplicate map entry a merge produced — a data defect in the map. This is about who may write it at all. **`component` left BLANK deliberately:** the finding sits between a workflow's write contract and a repo-wide doc test, and nothing scaffolded obviously owns that pair — `workflow-decomposition` owns the composition and invocation contracts but not a workflow's filesystem grant, and inventing a name here would commit `plan-candidates` to scaffolding a directory on a guess. **Done-state today: yes** — either remedy is a single small edit once the ruling is made, which is why this is a proposal awaiting a ruling rather than an issue awaiting a trigger.
