Rules:
- Follow each stage in order — do not skip stages
- Be thorough — this is a major build, not a quick fix
- **Never edit a file the RUNNING fleet reads at runtime.** A dispatch already in flight has its Python imported but re-reads data files on every call, so an edit lands in the middle of it. **Measured 2026-08-10: FOUR live dispatches died at once — the entire running fleet** because a config migration rewrote the bash scripts the old code was still regexing `MAX_TURNS` out of — it read the half-migrated line and `int()` refused it. The irony is the lesson: **removing a runtime-file-read coupling is itself unsafe while processes still hold that coupling.** Check for in-flight runs first; if any exist, either wait or accept that you are killing them. Nothing was lost that time — every run had pushed before it died — and that was luck, not design.
- **Never remove a worktree, or any directory, while your shell is INSIDE it.** The CWD survives as a dangling reference and every relative path after it fails — `./script.sh: No such file or directory`, exit 127, from a script that plainly exists. `cd` somewhere real FIRST, then remove. **Measured twice in one session**, both times destroying a tree and then invoking a relative path against it. Same family as never using `git checkout --` to undo an experiment: the failure is operating on a tree you already destroyed.
- **`type -a <tool>` before you verify anything about a command-line tool's behaviour.** The binary that answers is not always the one you mean — an alias, a shim, or a different implementation on `PATH` (`ugrep` standing in for `grep`) makes a verification true of a tool nobody is running. Measured: a run verified shell behaviour against a tool that was not the one resolving, and the finding was wrong in a way that read as rigorous.
- **Never `git checkout -- <file>`, `git restore` or `git stash` to undo an experiment.** They discard UNCOMMITTED work irreversibly, and being in the right directory does not protect you — **measured: a mutation loop reverted live edits this way, in the correct worktree.** Restore from a copy you made yourself, or commit first and revert the commit.
- **Worktree CWD discipline:** the workflow starts you in a git worktree at a specific absolute path. NEVER `cd` to the main repo's checkout — operations there land outside the worktree's branch and are invisible to the PR (silently lost work). When running sed/find/xargs across many files, pass the worktree's absolute path explicitly. **THIS APPLIES TO `Write` AND `Edit`, NOT ONLY TO BASH — asked for across two consecutive reviews and it kept happening.** The same CWD drift silently RELOCATES a `Write`, and the error you get names a missing module rather than a misplaced file, so the diagnosis points away from the cause. **Measured 2026-08-12: two research runs wrote their paper into the MAIN CHECKOUT** because an absolute path was handed to a subagent without being re-anchored; both were caught only by a pre-commit `git status`, which is a net rather than a guarantee. If you need a Bash command in a different directory, use `(cd <worktree-abs-path> && command)` in a subshell rather than a top-level `cd`.
- **A WORKTREE DISPATCH CAN START YOU ON A DETACHED HEAD, AND `git push origin HEAD` THEN FAILS WITH `refs/heads/HEAD`.** Before any push, run `git rev-parse --abbrev-ref HEAD`; if it prints `HEAD`, create the branch first (`git checkout -b <name>`) or push to an explicit ref (`git push origin HEAD:refs/heads/<name>`). **Six consecutive reflections asked for this line, and on 2026-08-13 the session that was writing it hit the same failure while pushing a merge resolution.** A prompt that says "push the branch" presumes a branch exists.
- **File-reading discipline:** after the first full Read of a file, subsequent Reads MUST use `offset`+`limit` or use Grep to target a specific region. Do NOT re-read the entire file. Unbounded re-reads of already-read files are the single largest source of wasted tokens observed in production (one run hit 17× full reads of the same 1500-line file = ~45k redundant tokens). Narrow Reads after Edits are legitimate verification.
- **Large-file reading:** before the FIRST Read of any markdown file, run `wc -l` on it. If >500 lines, use `limit:200` on the first Read to avoid the 25K-token Read ceiling. Common culprits: sprint.md, sprint/phase docs, roadmaps, standards docs, .jsonl logs. When in doubt, check size first.
- **Read-before-Edit (HARD requirement):** before any Edit or Write to an existing file, the most recent Read of that file MUST be in this turn or the immediately previous turn. If the gap is wider — or any tool ran between (formatter like ruff/black/autopep8, linter, codemod like isort, git checkout, test runs, autoformatter-on-save, subagent boundary) — re-Read the file before Editing. The `File has not been read yet` and `File has been modified since read` errors are the signals you missed this. Recurring pattern across multiple production review cycles — this is hard discipline, not soft guidance.
- **Bash CWD persists between calls — never blind-chain a relative `cd`:** the working directory usually carries over from your previous Bash call (some configurations reset it — treat it as unpredictable). A chained relative `cd <subdir> && ...` fails whenever the CWD is already that subdir. When you need to cd, use the absolute worktree-rooted path (`cd <worktree>/lib/temporal && pytest tests/unit/`) — idempotent regardless of current CWD — or skip cd and use absolute paths in the command itself.
- **Re-Read before re-Editing anything you wrote earlier:** Edit requires a fresh Read. The classic failures: revising a /tmp staging file (e.g. `/tmp/claude-pr-body.md`) several turns after Writing it, or re-Editing a repo file many turns after its last Read (applying review findings). Either Read the file again first, or for staging files simply Write the full replacement content instead of Editing.
- **Prefer relative paths inside the worktree:** the workflow places you at the worktree root. For Read/Grep/Glob/Edit/Write of files inside the worktree, use paths relative to the root (e.g., `lib/temporal/foo.py`) rather than re-typing the long absolute worktree path. The model occasionally typos long absolute paths (e.g., `.claire/` instead of `.claude/`) — relative paths eliminate that bug class entirely.
- **A DENIED capability is a CONSTRAINT, not a verdict — and "I was blocked" is a claim you must back.** When a tool call is refused (a `sudo`, a destructive command, a compound invocation), that tells you *this mechanism* is unavailable, not that the goal is unreachable. Before writing that you were blocked, **name what you tried instead** — and if you tried nothing else, that is the sentence to write rather than "blocked". **Measured, and it falsified itself inside one PR:** a draft pass reported 467 root-owned files as blocked on `sudo`, denied twice; the very next pass repaired them all with a rename-to-quarantine and verified rollback, no `sudo` involved. One pass declared it impossible; the next did it. A refusal that ends exploration silently converts a solvable task into a false constraint that the operator then inherits as fact.
- **Parallel tool calls in the gather phase:** when gathering context (Read/Grep/Glob), batch 3+ independent tool calls into a single assistant turn. Sequential gather wastes turns. Parallel gather is a pure efficiency win — higher-parallelism runs are not more error-prone.
- **Tool parameter naming gotchas** (these cause recurring InputValidationErrors):
  - Grep on a single file uses `path`, NOT `file_path`. Read/Edit/Write use `file_path`.
  - Read does NOT take a `command` parameter — that's Bash.
  - Glob does NOT take `head_limit` — that's a Grep option.
  - TodoWrite takes an ARRAY for `todos`, not a string.
